## 2026-08-22 Gateway v12 release-candidate addendum

The historical v1.3.0 evidence below predates the final v12 durable-dispatch candidate and must not be reused as current evidence. The v12 candidate now uses Gateway receive time for Live Activity durable admission/expiry while retaining producer `event_time` in the ActivityKit payload. Its frozen core submission includes the supplemental Live Activity snapshot, so a first-pass outbox failure preserves HTTP acceptance and remains pending for automatic, idempotent recovery. A database-issued acceptance order, allocated atomically with the durable submission, owns Widget and Live Activity latest-state precedence across same-millisecond concurrency, single-instance restart, and wall-clock rollback. Equal-order replay is accepted only for the same frozen submission generation. It also locks patched `h2 0.4.16`.

The single-instance compatibility boundary is explicit: audited v11 fails closed on schema v12; rollback before any v12 durable write requires restoration of the verified v11 snapshot; recovery after a v12 durable write is forward-only with the exact preserved v12-aware artifact. Existing v12 order watermarks self-heal above all positive persisted orders. Legacy zero-order pending submissions are not timestamp-backfilled because their true sequence is unknowable; candidate startup fails closed until the prior artifact drains them on an isolated/controlled recovery path. A materialized legacy zero-order outbox winner is preserved against other legacy generations, while future positive-order submissions can supersede it. See `release/V12_SINGLE_INSTANCE_ROLLBACK.md` and `scripts/v12_single_instance_rollback_drill.sh`. The temporary SQLite drill and focused SQLite/PostgreSQL/MySQL durability, ordering, recovery, and compatibility tests pass locally. Exact final-suite and synthetic restore-clone evidence are recorded above. Production backup/provider/device/canary evidence remains separate operational evidence and is not a publication gate for this release decision.

## Locked product boundaries

- Legacy `POST /messages/pull` remains destructive for beta-client compatibility.
- `POST /v2/messages/pull` is non-destructive. Clients fall back only for HTTP 404 with exact code `route_not_found`.
- `POST /messages/ack` accepts only the legacy single `delivery_id`. The separate `POST /v2/messages/ack` accepts `delivery_ids`; batch maximum is 200 and ACK is idempotent.
- Invalid, corrupt, or unsupported historical provider envelopes are silently omitted and deleted.
- APNs tokens are trimmed, validated as hexadecimal, and lowercased. FCM/WNS tokens are trimmed only and remain case-sensitive.
- Provider queue admission is best-effort/in-memory. `provider_queued` means worker-queue admission; provider success is recorded only after the provider send succeeds.
- Eviction of unacknowledged private outbox messages remains allowed by product definition.
- Android downgrade from stable `v1.3.0` to `v1.3.0-beta.1` is unsupported.
- Beta and stable Gateway processes must never share a database during upgrade or rollout.

## Implemented controls

### Pull and ACK data integrity

- Added non-destructive Pull v2 and retained the legacy destructive route.
- Kept single ACK on the legacy route and added a separate v2 batch ACK route with canonicalized/deduplicated IDs, a 200-item bound, and stable idempotent responses.
- ACK now deletes the provider queue row, linked private outbox row, and orphaned shared payloads in the same database transaction on SQLite, PostgreSQL, and MySQL.
- SQLite now removes expired rows before ACK just like PostgreSQL/MySQL.
- Invalid or unsupported historical envelopes are deleted after being omitted from Pull v2.
- Apple and Android persist the pulled message before ACK. Failed ACKs are retained and drained in later batches.

### Token identity

- APNs: whitespace trim, exact hexadecimal validation, lowercase canonical storage and lookup.
- FCM/WNS: whitespace trim only; case is preserved in API, route, history, and hashes.
- MySQL provider-token columns use binary collation and the existing 4096-byte business limit; binary-protocol text decoding is explicit so MySQL 8.4 cannot expose the value as an incompatible BLOB/VARBINARY.
- Historical APNs collisions are resolved deterministically by ascending update/create/hash order, making the newest binding the retained last writer.
- Cross-database parity now explicitly asserts FCM case preservation and APNs lowercase canonicalization.

### Delivery lifecycle and idempotency

- Added `provider_queued` sender status for worker-memory-queue admission.
- Provider success counters/status are updated only after the actual provider call succeeds.
- APNs expiration is converted from epoch milliseconds to epoch seconds.
- Client-supplied `op_id` is payload-bound. Exact retries reuse the semantic result; different payloads return `409 op_id_payload_conflict`.
- Sender status uses insert-if-absent ownership. MySQL classifies only error 1062 from a plain atomic insert as a duplicate instead of inferring ownership from affected-row flags. Duplicate or conflicting operations cannot rewrite the first operation's status, scope, entity, or timestamps.
- Known action-forbidden public DTO fields are rejected; genuinely unknown extension fields remain forward-compatible.

### Route, SQLite, MQTT, and upgrade safety

- Route transition and pending-delivery migration execute in one transaction for each backend.
- Provider-to-private migration refuses the entire transition with `409 route_transition_pending_capacity_exceeded` if every active provider row cannot fit; the old route and queue remain intact.
- Widget replace-all updates are transactional.
- SQLite core/delivery sidecar connections use rollback-journal mode, which preserves multi-file atomic commit semantics for attached databases; WAL-only tuning was removed.
- MQTT QoS 1 negative PUBACK retains the durable outbox item and triggers resynchronization. Only successful terminal PUBACK clears it.
- MQTT packet-ID wrap skips IDs still owned by in-flight deliveries.
- Managed no-op verification is read-only for an already-current schema; beta1 v9 databases follow the real managed migration to the current binary target (v10 for this release).
- PostgreSQL/MySQL backup manifests name the exact database-URL fingerprint and driver, must declare a completion time no older than 24 hours, and must reference a readable absolute local artifact. Gateway streams the bytes and verifies exact size and SHA-256 before migration. This is operator-supplied artifact admission evidence; it does not independently attest source-database provenance or restorability.
- Release CI runs all-feature Clippy and `cargo audit`; dependency updates remove the disclosed advisory found during the audit.

## Red/blue audit rounds

### Round 1: protocol and compatibility

Red-team attacks: destructive-vs-non-destructive route confusion, broad fallback on arbitrary 404, ambiguous ACK bodies, duplicate ACK IDs, oversized batches, corrupt/future envelopes, and phone/watch delivery-ID overlap.

Blue-team result: exact route fallback, strict ACK shape and bound, atomic idempotent deletion, explicit device-scoped ACK, direct database assertion that invalid rows are deleted, and Apple/Android contract tests. No unresolved protocol defect remains within the locked boundary.

### Round 2: data races and crash windows

Red-team attacks: provider success before send, route switch after partial migration, Widget partial replacement, op-id status ownership theft, MQTT negative PUBACK loss, packet-ID wrap collision, and SQLite attached-database crash atomicity.

Blue-team result: separate queued/sent lifecycle, transactional route/widget operations, capacity fail-closed, insert-if-absent sender-status ownership, durable negative-PUBACK retention, collision-free packet allocation, and rollback-journal sidecars. Regression tests cover each discovered failure mode.

### Round 3: storage and release adversary

Red-team attacks: FCM case folding on MySQL, nondeterministic APNs collision repair, expired ACK backend drift, stale/self-attested backup manifests, v9 no-op startup failure, vulnerable dependencies, version/feed mismatch, and accidental beta/stable mixing.

Blue-team result: binary MySQL token semantics, binary-protocol-safe token decoding, deterministic history selection, uniform expired-row handling, byte-verified recent operator-supplied backup artifact admission, read-only no-op upgrade, audited dependency graph, stable version metadata and tag gates, and explicit rollout prohibition on mixed Gateway versions.

The live adversarial run additionally reproduced and eliminated the MySQL token decode panic and affected-row ownership bug. After both fixes, all three rounds produced pairwise-identical API summaries and database summaries, with identical normalized hashes on every backend.

## Production rollout order

1. Keep every Gateway process stopped; do not mix beta and stable binaries.
2. Preserve the beta binary, exact configuration, credentials, and a restore-tested database backup.
3. Run `--db-upgrade plan` and review driver, source schema, target schema, and backup policy.
4. For PostgreSQL/MySQL, mount or download the immutable backup artifact, generate the v1 manifest, and run `--db-upgrade run` with one process.
5. Start one stable Gateway canary and verify health, Pull v2, ACK, provider queued/sent counters, and send-status behavior.
6. Roll out stable Gateway instances, then Apple and Android stable clients.
7. Monitor provider send failures, ACK backlog/retries, invalid-envelope deletion count, route-transition conflicts, MQTT negative PUBACKs, and sender-status conflicts.

Gateway rollback requires restoring the pre-upgrade database backup and running only the preserved beta binary. Android client downgrade is intentionally not supported.
